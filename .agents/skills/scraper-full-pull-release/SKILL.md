---
name: scraper-full-pull-release
description: Prepare, monitor, repair, and verify an authorized ScraperProject production full pull before publishing its changes. Use when the user requests a complete seasonal snapshot or release validation.
---

Read PROVIDER_UPGRADE_VALIDATION.md, PULL_IMPROVEMENTS.md, and any LIVE_FULL_PULL_RUN_REPORT.md before running. Use scraper-provider-parity for provider edits, scraper-live-parity for acquisition/filter changes, and scraper-pull-recovery for persistence changes. A production run needs explicit user authorization; authorization already given in the conversation persists.

Preserve strict future starts. Unless the user specifies a date bound, include every valid future event without an end-date cutoff. Inspect saved provider URLs and browser seed parameters for stale season limits. Refresh existing records and create a new complete snapshot, with a distinct run manifest. Back up ledgers and existing logs to ignored local storage before the first run; never reset ledgers or expected fixtures to hide failures. Keep captures, source credentials, browser cookies, workbooks, and runtime ledgers out of Git.

Run the appropriate tests and template preflight. On Windows use scripts/run_full_pull.ps1: native stdout/stderr redirection avoids PowerShell formatting large error streams. Monitor both log files and the exact Sheets/PullRuns manifest. Do not infer completion from a quiet console or a launcher exit; check the scraper process, provider logs, manifest, and exit code. A crashed launcher can leave its scraper child running. Never start another production ledger writer while it remains alive.

Distinguish verified empty results, unpublished optional data, invalid source fields, HTTP blocking, incomplete pagination, dead browser sessions, and export/checkpoint failures. Capture a bounded failing example, freeze current source, apply one narrow fix, replay valid before/after outputs, and add a source-grounded failure or corrected-layout expectation. A plain HTTP probe without the browser's bootstrap cookies does not prove a browser-backed provider is broken. Retain pending exports and completed output. If stopping an already failed diagnostic is necessary, identify only its owned processes, preserve recovery state, and record the attempt as interrupted; do not certify it.

Code edits do not change modules already loaded by a running pull. Verify them in a fresh run. For early listing date skips, require explicit dates for every child, keep mixed/unknown groups, and preserve non-future accounting. Preserve legacy discovery when supplementing it with a newer API; retain event identities, source filters, grouped fields, and completion metadata. Do not assume pagination or filter parity from one successful response.

After the original process finishes, retry today's partial/interrupted snapshot with `main.py --repair-snapshot Sheets/PullRuns/<run-id>.json` (or the native launcher with `-RepairSnapshot`). Repair holds the ledger lock, archives the previous manifest, retains successful locations and the original output/date settings, and records each attempt. Never use new date settings to repair an old snapshot; a new calendar day requires a new run. Explicit source placeholders such as DATE TBD may be recorded as retryable source exclusions: retain URL/reason, count them separately, export no invented dates, and verify rediscovery can later restore valid data. Ordinary parsing or validation failures remain failures.

After completion run:

```powershell
.\.venv\Scripts\python.exe scripts/audit_snapshot.py Sheets/PullRuns/<run-id>.json --report Tests/full_pull_monitor/<run-id>_audit.json
```

Require all expected providers/locations accounted for, complete coverage, no unresolved current-run validation/extraction/persistence failures, valid 56-column rows, strictly future dates, matching manifest/workbook counts, unique indexed identities per destination, location membership, and acknowledged exports. Cross-location membership may legitimately repeat an event. Verified empty locations may have no workbook. Optional blanks must reflect the source rather than inferred values. Also check provider consolidations and downstream import constraints relevant to the change.

After all writers stop, compare the stable pre-repair copy with the final same-date snapshot using `python scripts/compare_snapshot_fields.py BEFORE AFTER REPORT.json`. It checks all 56 indexed fields, including optional contacts, and reports additions separately. Investigate every removed identity or changed field. Capture the current source to distinguish published updates from acquisition loss; document intentional source changes rather than editing the baseline or calling a nonzero comparison exact parity. A schema audit alone cannot certify optional-field preservation. Recover published contacts from verified pages; unrecognized detail bodies must fail visibly rather than erase fields. Never read active workbooks for this comparison or overwrite production ledgers with stale baseline values.

Record attempted run IDs, exact coverage/rows, fixes, parity evidence, skipped versus failed work, and remaining limitations in LIVE_FULL_PULL_RUN_REPORT.md. Publish only after the user's stated acceptance condition is satisfied and publishing is authorized. Conditional authorization from the current conversation is sufficient; do not request it again. Review the final diff and artifacts, run required checks, and use the configured GitHub remote. Link every created/worked PR through the available thread-link tool immediately, then verify thread PR registration before finishing.

When a grouped URL redirects to a single published division, compare the original grouped export contract with the direct-event parser. Preserve source-verified venue and competition fields and justified grouped defaults without changing ordinary single-event inputs. Capture unpublished former divisions separately; do not restore them from stale ledger data. Freeze direct-input output before editing and test all columns unchanged, plus source-backed grouped corrections. A transient contact-page failure must still be retried and verified in the production repair; a successful private probe alone cannot certify the snapshot.

For an intermittent detail navigation failure with a blocked HTTP fallback, a single additional browser navigation may recover the published page. Require the same recognition guard, existing timeouts, valid-input parity without extra navigation, and a test that persistent unverified bodies fail after the finite retry. Propagate dead-session errors to the runner's existing driver recovery.
